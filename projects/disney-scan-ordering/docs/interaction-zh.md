# 上海迪士尼 App｜扫码点餐交互说明

文档性质：基于现有设计资料整理的作品集复盘稿。原稿明确的规则标注为「设计资料可确认」；为完善交付而补充的规则标注为「建议规则」；尚无完整设计材料的业务标注为「待确认」。本文不代表当年完整上线规格。

## 1. 业务目标与设计范围

承接上海迪士尼园区内不同餐饮场景的移动点餐服务，通过内嵌 App 的 HTML 页面连接原生入口与点餐业务，并支持中文、英文。

我的角色：设计团队负责人、项目主导，负责体验方向、团队设计推进与交付把控，并直接与美国迪士尼团队协同。以下复盘着重说明业务入口、用户路径与设计判断。

设计资料可确认：App 入口、餐厅列表与详情、扫码分流、登录衔接、营业判断、菜单、套餐配置、购物车与支付入口，以及订单和核销相关入口说明。支付渠道、完整支付结果页面和履约规则仍待确认。

## 2. 用户与任务情境

家庭同行游客：需要为成人和儿童一起选餐，理解套餐份量及必选项。

时间受限游客：希望在游玩或排队间隙迅速找到可用的点餐服务。

中英文游客：需要在相同业务路径中准确理解餐品、规格、价格和操作反馈。

以上为设计情境归纳，不代表已开展访谈或量化用户分群。

## 3. 入口与二维码分流

| 入口 / 码类型 | 设计资料可确认的路径 | 交互重点 |
| 移动点餐 Mobile Order | Dashboard、订单列表入口进入餐厅列表 | 先选餐厅，再进入对应业务 |
| 餐厅详情 Order Food | 营业中进入菜单；停业进入欢迎页 | 在欢迎页说明暂停营业，并提供返回餐厅列表入口 |
| 我的点餐 My Food Order | Dashboard、确认页可进入订单列表 | 已有订单可重新找到；具体订单状态待确认 |
| 通用二维码 | 扫码后进入移动点餐餐厅列表 | 不把通用码误识别成某一家门店 |
| 门店专属二维码 | 进入该门店的菜单或停业欢迎页 | 保留门店标识，进入前判断服务状态 |
| 餐桌二维码 | 携带餐桌场景进入相应点餐链路 | 餐桌标识及服务模式需与后台确认 |
| QSR 核销二维码 | 进入核销结果页并获得四位取餐号 | 不与点餐入口混用；核销条件及重复扫码规则待确认 |

原稿还区分迪士尼 App、口碑 App 与其他第三方扫码后的承接路径。其表述属于当时方案背景，外部应用的现行能力不在本次复盘确认范围内。

## 4. 主路径与分支

路径 A：App 移动点餐入口 → 餐厅列表 → 餐厅详情 → Order Food → 登录校验 → 营业状态判断 → HTML 菜单。

路径 B：App 扫码 → 识别二维码类型 → 通用码进入餐厅列表；门店码 / 餐桌码进入指定服务上下文 → 登录校验 → 营业状态判断 → HTML 菜单。

路径 C：菜单 → 查看餐品 → 完成套餐 / 规格选择 → 加入购物车 → 核对金额与数量 → 支付入口。后续完整支付与履约路径待补充原始材料。

建议规则：登录完成后继续原目标路径；取消登录时保留可恢复入口；停业或扫码异常提供可执行的返回、重扫或选店操作，避免用户停在无后续动作的页面。

## 5. 菜单与选餐

设计资料可确认：页面包含门店信息、商品与优惠券入口、餐品分类、图片、名称、价格、规格选择和底部购物车 / 支付区域。单品有直接加购和需选择配置两种表现。

建议规则：进入菜单先明确当前门店和服务信息；切换分类时同步选中态与内容位置；加减数量后同步更新列表数量、购物车数量与金额。空购物车不能继续支付。价格、库存及可售状态以服务端校验为准。

设计判断：让游客在浏览餐品时持续看见当前选择与金额，减少为确认已选内容而反复切换页面。

## 6. 套餐与规格选择

设计资料可确认：套餐弹层包含餐品介绍、成人 / 儿童饮品分组、Select N 数量要求、展开更多、饮品冰量等必选规格、套餐数量及 Add 按钮。部分示例含英文占位文案，应以最终内容为准。

建议规则：每个分组显示「已选数量 / 要求数量」；未满足所有必选项时 Add 不可提交，并指出缺失的分组或规格。达到数量上限后限制继续增加，同时允许减选和替换。

建议规则：同一饮品不同规格独立呈现；再次打开已有配置时回显选择；弹层关闭与返回行为一致。选择数量、规格与价格变化的联动方式需与产品、开发确认。

设计判断：把复杂套餐拆成可逐项完成的选择任务，帮助家庭游客区分成人和儿童餐品，降低漏选与误选风险。

## 7. 购物车、支付与订单边界

设计资料可确认：底部区域展示购物车、数量、金额与 Payment 入口；原始说明中存在确认页、订单列表和 QSR 核销结果页。

建议规则：支付前复核门店、商品、套餐规格、数量、优惠及应付金额；阻止重复提交；请求失败时保留已有选择并给出重试入口。

待确认：支付渠道、优惠券叠加及计算规则、支付取消 / 失败 / 处理中状态、重复支付防护、支付结果返回方式、订单状态、取餐通知、退单退款及堂食服务流程。不可仅凭 Payment 按钮推断这些流程已经完成设计或上线。

## 8. 状态与异常反馈

| 状态 | 建议用户反馈 | 恢复方式 / 需确认事项 |
| 首次加载 | 明确加载状态，避免显示成空白页 | 保留原生返回；超时可重试 |
| 二维码无效 / 失效 | 说明未识别有效点餐码 | 重新扫码或选择餐厅；码有效性规则待确认 |
| 登录中断 | 说明尚未完成登录 | 重试登录；是否允许访客浏览待确认 |
| 门店停业 | 明确当前不可点餐 | 返回餐厅列表；此分支原稿已有说明 |
| 必选项未完成 | 在对应分组提示还需选择的数量 / 规格 | 定位未完成项，保留其他已选内容 |
| 商品售罄 / 价格变更 | 说明受影响餐品及最新金额 | 刷新并重新确认，不能静默替换 |
| 网络异常 | 说明加载或提交失败 | 保留选择并重试；写入请求先确认结果 |
| 支付结果未知 | 引导查询订单结果 | 不直接提示再次付款；最终业务协议待确认 |

## 9. 中英双语与 App 内嵌协同

建议规则：页面语言继承 App 设置；切换语言保留门店与选餐状态；餐品名、规格、错误提示统一维护双语映射；金额单位与时间表达清楚。示意图中的货币符号不能直接作为真实结算币种的证据。

建议规则：关闭餐品弹层、返回菜单和退出 HTML 页面分层处理；原生与 HTML 对齐登录凭证、二维码上下文、语言、导航返回、加载失败及支付结果回传协议。具体技术方案与权限范围需由相关团队确认。

## 10. 交付与验证清单

交付建议：入口矩阵、码类型与路由规则、页面与弹层状态、套餐选择规则、异常恢复说明、中英双语文案表、原生与 HTML 协议清单。

验证重点：不同码型能否到达正确服务；停业分支能否退出；登录后是否回到原目标；套餐分组数量是否正确；规格是否随购物车保留；返回是否误清空；双语长文案是否溢出。

建议关注入口到菜单成功率、加购完成率、套餐配置中断率、支付发起率与异常恢复率。当前没有这些指标的实测结果，不将其写为项目成效。
